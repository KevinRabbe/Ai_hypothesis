## Branch A — capability confirmation fails

Condition:

- confirmation artifacts are valid;
- fewer than 12/12 frozen primary seed × comparison CIs satisfy `CI_low > 0`.

Interpretation:

> Gate-2 v0 does not confirm the organization-specific capability claim.

Actions:

- preserve the full negative/mixed confirmation result;
- do **not** run the resource benchmark as an attempt to rescue Gate 2;
- do not open Gate 3;
- inspect which causal comparison/seed failed;
- decide whether the result supports a narrower mechanism claim or whether Gate-2 development should stop;
- any changed training/workload/model becomes a new development/protocol version and may not reuse the exposed confirmation worlds as fresh confirmation.

Gate 0 and Gate 1 retain their narrower established claims.

## Branch B — capability passes, resource half fails mechanically

Condition:

- 12/12 capability confirmation passes;
- resource correctness preflight fails decoded schedule identity, learned-work identity or state-bank identity; or admitted measurement provenance is invalid.

Interpretation:

> Capability is confirmed, but the v0 resource experiment is mechanically invalid/incomplete. No overall Gate-2 v0 verdict yet.

Actions:

- preserve capability confirmation as confirmed capability evidence;
- preserve failed resource attempt separately;
- diagnose the execution/mechanics boundary without changing capability weights/workload;
- freeze a new resource protocol version before another admitted timing run if required;
- Gate 3 remains locked because Gate-2 v0 requires both halves.

## Branch C — capability passes, valid resource result fails practical endpoint rule

Condition:

- 12/12 capability confirmation passes;
- resource artifact is valid;
- one or more of C64/W64 B1, C64/W64 B64, C256/W256 B1, C256/W256 B64 does not have lower parallel median latency than serial.

Interpretation:

> Persistent-state population organization has confirmed capability value on the frozen task, but Gate-2 v0 is **not positive as a capability + practical-resource architecture result** on the eager RTX 4060 Ti baseline.

Actions:

- preserve the confirmed capability claim explicitly;
- mark overall Gate-2 v0 not positive because the frozen resource half failed;
- do not redefine the endpoint rule after timing;
- a compiler/graph/fusion study may be run later as a **separate systems experiment** using the exact confirmed function;
- Gate 3 remains locked until the project decides whether a later execution-mode result is allowed to define a new Gate-2 version.

## Branch D — capability and resource halves both pass

Condition:

- all 12 capability confirmation comparisons pass their frozen CIs;
- every resource preflight passes;
- no OOM/unrecoverable resource failure;
- all four decision endpoint cells favor parallel median latency.

Interpretation:

> **Gate 2 v0 is positive.**

Supported claim is intentionally narrow:

> On the frozen delayed-keyed-traces benchmark, three independently trained fixed-parameter shared-weight organisms reproducibly gain held-out capability from larger stable persistent runtime state under matched inspected information and matched learned recurrent-update count; breaking locality or persistence removes much of that advantage; and the confirmed function has a useful eager-CUDA parallel execution frontier over the mathematically matched serial persistent schedule on the RTX 4060 Ti.

This still does not establish general intelligence scaling, real-workload advantage, optimal population size, compiler advantage, or populations above 256.

Actions:

1. write the immutable Gate-2 confirmation/result record and independent audits;
2. archive hashes/provenance;
3. update canonical README/roadmap from `Gate 2 active` to `Gate 2 completed positive`;
4. unlock Gate 3 as the next scientific gate;
5. keep compiler optimization a separate systems variable rather than silently changing the Gate-2 baseline.
